## Executive decision

The site is technically clean where the existing tests look (one `h1`, `lang`, canonical + symmetric `en`/`cs`/`x-default` hreflang on all 22 static pages, real `noindex` 404s, HSTS preload, Lighthouse SEO and Best Practices 100 on all 13 sampled URLs) and it owns its brand queries in Google and Seznam. It is invisible where nobody looked: **sampled Bing searches return no codeguy.cz result at all** (`site:` and the name query), **neither published article appears in Google's `site:` results**, every portfolio page ships **without `og:image`/`og:site_name`** and with the Home text in its Twitter card, the article covers that do exist sit under a **robots-disallowed path**, **no structured data** exists, the language switcher provides **no crawlable cross-locale link** (it is a `<button>`; the only path between the halves runs through the English-only articles), and **no search-engine or client measurement exists** — no Search Console, no Bing Webmaster, no analytics (Caddy access logs are the only record), so none of this was observable from inside the project. The indexation statements are search samples, not index inventories; they become facts only once the consoles exist. Twelve of 24 canonical pages carry a bare section-label title ("About | Codeguy") that Google rewrites; the site appears in the top 30 for none of nine role + location queries, while Seznam does rank individual developers for the Czech ones. Mobile lab LCP is 3.2–4.6 s on every page (desktop 0.8–1.2 s); field data could not be obtained.

Order of work: first establish search-console coverage (P0 — until it exists, none of the indexation findings can be settled); then the confirmed metadata and crawl-path defects (P1: social previews, the robots rule over the article covers — whose effect on real fetchers is untested — article discovery, cross-locale linking, generic titles). The CV PDF's search exposure is an owner decision, not a defect. Everything else can wait for Search Console data.

## Detailed findings

### SEO-001 — `og:image` and `og:site_name` missing on every portfolio page

- Evidence: 32 of 34 crawled HTML pages have no `og:image` and none of 34 has `og:site_name`; only the two CMS articles carry an image (their own cover). Confirmed by curl on `/`, `/cs`, `/about`, a case study and `/insights`.
- Problem: `createLocalizedMetadata` (`src/i18n/metadata.ts:19-48`) returns a complete `openGraph` object; Next.js merges metadata per top-level key, so the page object replaces the layout's `openGraph.images` and `siteName` (`src/app/[locale]/(frontend)/layout.tsx:28-97`). The existing `i18n-seo.spec.ts` asserts `og:locale`, `og:type` and `og:url` but never `og:image`, which is why this passed every gate.
- Impact: every share of the Home, About, Work, CV or Contact page on LinkedIn, Slack, Teams, iMessage or X renders without an image — the exact surfaces a recruiter forwards a candidate on. LinkedIn additionally falls back to any large image on the page; the portfolio pages have none.
- Risk of fixing: the metadata change is small; the chosen image and its crop need a brand check and a real consumer check (LinkedIn Post Inspector) before the fix is called done.
- Recommendation: in `createLocalizedMetadata` spread `images` and `siteName` (or accept them as parameters and default to the site image); add `og:image`, `og:image:width/height`, `og:site_name` assertions for Home, a case study and the CV to `src/__tests__/e2e/i18n-seo.spec.ts`; add a unit test in `src/__tests__/unit/i18n-metadata.test.ts` asserting the merged object.
- Smallest fix location: `src/i18n/metadata.ts`; tests above.
- Dependencies: SEO-002 decides which image; SEO-001 can ship first with the existing 512 icon so previews are at least branded.

### SEO-002 — No 1200×630 social image exists

- Evidence: the only social asset is `/web-app-manifest-512x512.png` (512×512, 14.9 kB), used as `twitter:image` with `summary_large_image` on every portfolio page. CMS covers are 1200×630.
- Problem: a square app icon in a `summary_large_image` slot is cropped or letterboxed by every consumer; there is no per-page or site-wide 1200×630 asset and no `opengraph-image` route.
- Impact: brand-less previews; combined with SEO-001 the current state is "no image" on most consumers.
- Risk: a generated image must obey the brand system (`docs/brand/brand-guidelines.md`, mark decision BD-20 still open per memory) — this is a design decision, not just an asset.
- Recommendation: owner decides between (a) one static 1200×630 brand image for all portfolio pages, (b) a Next.js `opengraph-image.tsx` rendering name + role + page title from tokens, or (c) per-route Figma frames. (b) keeps text in catalogs and tokens in `variables.css`, consistent with how the CV PDF is generated.
- Smallest fix location: `src/app/[locale]/(frontend)/opengraph-image.tsx` (option b) or `/public` asset + `layout.tsx` (option a).
- Dependencies: brand decision; SEO-001.

### SEO-003 — No search console for any engine; no Bing result in sampled searches

- Evidence: Bing `site:codeguy.cz` returns no codeguy.cz result (fallback results only; the displayed count is for the fallback set); Bing `"Karel Kutchan"` top 10 has LinkedIn, GitHub, Instagram and four register sites but not codeguy.cz. DuckDuckGo (Bing-fed) could not be queried via curl (bot gate) — not verified directly. Google shows the "Do you own codeguy.cz? Try Search Console" promo on `site:` queries, i.e. no verified owner; the repo has no verification token, and `docs/` has no record of either tool.
- Problem: the sampled searches say Bing serves nothing from the domain; why (never discovered, crawled but not indexed, or sampling) is unknown until Bing Webmaster's crawl and sitemap reports exist. More fundamentally, nothing in the project can see indexation, impressions, queries or crawl errors for any engine.
- Impact: the sampled Bing searches found no site result; visibility across Bing-powered products (DuckDuckGo, Ecosia, Copilot) is unmeasured and presumably similar. Every content or keyword decision in this audit is a hypothesis until Search Console data exists (`docs/content/article-backlog.md:10-11` already forbids inventing volumes).
- Risk: none; verification is a DNS TXT record.
- Recommendation: see "Measurement stack". Domain property in Search Console (DNS TXT), import to Bing Webmaster, submit `/sitemap.xml` to both, request indexing for `/`, `/cs` and both articles. Record the day-one coverage snapshot as an addendum here.
- Smallest fix location: DNS provider + the two consoles (Karel). No code.
- Dependencies: none. Unblocks SEO-004, SEO-011 (CrUX in GSC), SEO-016.

### SEO-004 — Published articles do not appear in Google `site:` results

- Evidence: Google `site:codeguy.cz/insights/` → exactly one result, the listing. `gemini-4-argon-workflow-can-wait` was published 2026-10-02, `what-you-pay-for-…` 2026-10-08. Both are in the sitemap (`priority 0.6`, no hreflang), return 200, `index, follow`, canonical self. They differ from the other pages in three ways: no `googlebot` meta (`max-image-preview:large`), `Cache-Control: private, no-cache, no-store`, and only two inbound links (the two listings, both at depth 1).
- Problem: a `site:` sample is not an index inventory, so "not indexed" is a hypothesis; six days without a `site:` hit for a 1,500-word article on a domain whose other 20 pages do show up is consistent with discovery/priority rather than a block: no inbound links except the listing, sitemap `lastmod` noise (SEO-014), no submission channel, and the cover image under a robots-disallowed path (SEO-029). Only URL Inspection can say which.
- Impact: neither article appeared in the sampled `site:` results, so the Insights section — the fifth nav item and the only growing content — has no observed search footprint; its index status and impressions are unknown, and the article roadmap's "Search Console observation after publishing" step is impossible today.
- Risk: none.
- Recommendation: after SEO-003, run URL Inspection on both articles and record the verdict (Discovered/Crawled/Indexed, canonical chosen by Google). Independently of that: fix SEO-014, link articles from the Home or relevant portfolio pages (SEO-017/022), add `BlogPosting` JSON-LD (SEO-007), and add the `googlebot` meta for parity with the other routes.
- Smallest fix location: `src/app/[locale]/(frontend)/(pages)/insights/[slug]/page.tsx:39-97` (`robots.googleBot`), `src/app/sitemap.ts`.
- Dependencies: SEO-003 for the diagnosis; SEO-014, SEO-017.

### SEO-005 — No crawlable path between the English and Czech site

- Evidence: EN pages contain zero `href` starting with `/cs`; CS pages contain zero links to EN section pages (only the English-only article URLs). The switcher in `src/app/(frontend)/components/ui/languageSwitcher/index.tsx:35-39` is a `<button onClick>` calling `replaceDocument(href)`. In the crawl, all 17 `/cs*` URLs are unreachable from `/`; from `/cs`, EN pages sit at depth 3–4 via the articles.
- Problem: cross-locale discovery relies on `hreflang`, the sitemap and the indirect path through the English-only article links. Google did index `/cs` pages (hreflang works); a crawler that ignores hreflang, or a user with JS disabled, has no direct link from any English page to its Czech twin or back.
- Impact: Seznam — the engine that actually ranks individual developers for Czech queries (SEO-016) — currently indexes mostly `/cs` pages and only `/` + the PDF from EN; the EN half is nearly invisible to it.
- Risk: changing the switcher touches a locked localization contract (L-01/L-02 in `docs/decisions/localization.md`); rendering `<a href>` must keep the current `replaceDocument` behaviour for query/hash preservation (`i18n-routing.spec.ts` asserts query survival).
- Recommendation: render the switcher options as real anchors whose `href` is the value the component already computes with `getPathname` (`languageSwitcher/index.tsx:27-28` — unprefixed for EN, `/cs…` for CS, query and hash preserved), with `hreflang` and `lang` attributes, progressively enhanced by the existing click handler. Do not use `Link` with a `locale` prop: under `localePrefix: 'as-needed'` next-intl emits `/en/…` for the default locale in that case, which here lands on the `/en` 307 (SEO-015). Add a routing test asserting an `<a href="/cs…">` exists on `/` and an `<a href="/…">` (literal, unprefixed) on `/cs`, and that the query survives.
- Smallest fix location: `languageSwitcher/index.tsx`; `src/__tests__/components/language-switcher.test.tsx`; `i18n-routing.spec.ts`.
- Dependencies: none.

### SEO-006 — Generic section-label titles; no location keyword anywhere

- Evidence (Annex A): titles `Work | Codeguy`, `Experience | Codeguy`, `About | Codeguy`, `Contact | Codeguy`, `Insights | Codeguy`, `Curriculum Vitae | Codeguy` and the six Czech equivalents — 12 of 24 canonical pages. "Karel Kutchan" is in the title of 2 pages (the Home pages). "Prague"/"Praha" appears in 0 titles and 4 descriptions. Google rewrites the section titles in its results to "About - Senior Frontend Engineer | Codeguy" (observed on `site:` SERP), i.e. it considers the live title insufficient and borrows from the Home title. Of 8 ranking personal sites sampled, 8/8 use `Name – role phrase` titles; Czech ones carry the exact tokens "frontend vývojář"/"React vývojář".
- Problem: the title template is `%s | Codeguy` with `%s` = the nav label (`messages/en.json` `*.metadata.title`). The `h1` differs from the title on 8 of 13 EN and 8 of 11 CS pages, and the CV `h1` is the bare name.
- Impact: the page a recruiter lands on from a search shows a label, not a proposition; Google's rewrite is not controllable and not applied by Bing/Seznam.
- Risk: titles are catalog copy; the Home title and `h1` are locked (HP-01, approved copy fixture `src/__tests__/e2e/support/approved-copy.ts`). Section titles are not covered by a decision record — but they are copy, so Karel decides the pattern, not the agent.
- Recommendation: owner picks a pattern such as `<Section> — Karel Kutchan, Senior Frontend Engineer, Prague | Codeguy` (EN) / `<Sekce> — Karel Kutchan, senior frontend vývojář, Praha | Codeguy` (CS), applied via `metadata.title` keys in both catalogs; keep the brand `h1`s. Pair with SEO-016's keyword hypotheses. Add the chosen strings to the approved-copy fixture only if a decision record locks them.
- Smallest fix location: `messages/en.json`, `messages/cs.json` (`work|experience|about|contact|insights|curriculumVitae.metadata.title`); `i18n-seo.spec.ts` title assertions.

### SEO-029 — Article cover images live under a robots-disallowed path

- Evidence (2026-10-21, found by the Codex review, confirmed by the controller): `robots.txt` has `Disallow: /api/`; both articles declare `og:image` as `https://codeguy.cz/api/media/file/<cover>.png`; `GET` on each returns 200 `image/png`, `HEAD` returns 404. The images are also the LCP element on `/insights` and the article (SEO-011).
- Problem: a robots-compliant image fetcher (Googlebot-Image, Bingbot) is told not to request the only images the site offers for previews and rich results. The Payload media route sits under the same `/api/` rule that asks compliant crawlers to avoid the CMS API (robots.txt is a crawl instruction, not access control). Separately, the route answers `HEAD` with 404 — a server behaviour the robots rule does not touch.
- Impact: the two pages that *do* have social images (the exceptions to SEO-001) may render without one in Google Discover / image search, and the article thumbnails cannot be indexed by compliant engines. Which consumers are affected has not been tested: a scraper that ignores robots.txt can still fetch the image by `GET`; whether any relevant fetcher needs a successful `HEAD` is unproven.
- Risk: `Allow: /api/media/file/` narrows the API protection by one prefix; the media route stays rate-limited by `src/proxy.ts`. Serving covers from a non-API path is a Payload upload-path change.
- Recommendation: add `/api/media/file/` to the `allow` array in `src/app/robots.ts` (`allow: ['/', '/api/media/file/']`; Google and Bing resolve conflicts by the longest matching path, so the `Allow` wins over `Disallow: /api/` regardless of order — unit-test the emitted file), then verify with a robots tester and, once SEO-003 is done, with Search Console URL Inspection's fetched-resources view. Treat `HEAD` support on the media route as a separate, conditional item: fix it only if a relevant fetcher is shown to need it. Longer term, consider serving media from `/media/` via a rewrite so the API rule stays whole.
- Smallest fix location: `src/app/robots.ts` (`allow` array). `HEAD`: Payload media route, conditional.
- Dependencies: SEO-003 for verification.
